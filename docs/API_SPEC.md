# Rewards API specification

This is the implemented backend API contract for all four use cases in [CHALLENGE.md](CHALLENGE.md): view a points balance, browse rewards, redeem a reward, and view redemption history. Authentication is out of scope. The backend implements this contract and tests it with Rails integration tests.

## Conventions and demo identity

- Base URL for local Rails: `http://localhost:3000`. The frontend can use relative `/api` URLs through the Vite development proxy.
- All `/api` requests require `x-user: <user_id>`. Header names are case-insensitive. The value must be one positive decimal integer (for example, `1`), without signs, leading zeros, or multiple values. The referenced user must exist.
- `x-user` selects the demo user; it is not authentication or authorization. Any caller can choose any existing user ID. Balance and history are always scoped to this header, and redemption always debits this user. User IDs are not accepted in paths or request bodies in this implemented contract.
- Redemption POST requests also require `Idempotency-Key: <UUID v4>`, generated by the frontend for one intended redemption. Read endpoints do not require this header.
- Responses use `Content-Type: application/json`. POST requests must use `Content-Type: application/json` (an optional charset parameter is allowed). Clients should send `Accept: application/json`.
- JSON field names use `snake_case`. Response IDs, balances, costs, and points spent are JSON integers. Balances are nonnegative; costs and points spent are positive. Timestamps are ISO 8601 strings in UTC.
- Collection responses are arrays, with `[]` for an empty collection. Pagination, filtering, reward administration, and user administration are outside the challenge scope.
- Examples below are illustrative; balances and records depend on the current database state.

## Endpoints

| Use case | Method | Path | Success |
| --- | --- | --- | --- |
| View the selected user's balance | GET | `/api/balance` | `200 OK` |
| Browse active rewards | GET | `/api/rewards` | `200 OK` |
| Redeem a reward for the selected user | POST | `/api/redemptions` | `201 Created` |
| View the selected user's redemption history | GET | `/api/redemptions` | `200 OK` |

### GET /api/balance

No request body or query parameters. Returns the current stored points balance and basic demo-user information.

```http
GET /api/balance
x-user: 1
Accept: application/json
```

```json
{
  "user_id": 1,
  "name": "Alex Morgan",
  "points_balance": 1250
}
```

Errors: `400 missing_user_header`, `400 invalid_user_header`, `404 user_not_found`.

### GET /api/rewards

No request body or query parameters. Returns all active rewards, ordered by `points_cost` ascending, then `id` ascending. Availability means active, regardless of whether the selected user can afford the reward. Inactive rewards are excluded. The client can compare costs with `/api/balance`; a listed reward can still become unavailable before redemption.

```http
GET /api/rewards
x-user: 1
Accept: application/json
```

```json
[
  {
    "id": 1,
    "name": "Free coffee",
    "description": "One complimentary coffee.",
    "points_cost": 250
  }
]
```

`description` is a string or `null`. Each reward includes only the four fields shown above.

Errors: `400 missing_user_header`, `400 invalid_user_header`, `404 user_not_found`.

### POST /api/redemptions

Creates at most one successful redemption per user and idempotency key using the selected user's points. Send `reward_id` in a JSON object as a positive integer or a decimal string matching `[1-9][0-9]*`. Missing IDs, booleans, floats, zero, negative values, whitespace, leading zeros, and strings with trailing text return `422 invalid_request`. Empty bodies and non-object JSON without a reward ID also return this error. Only the JSON body's ID is used; query parameters and additional body fields are ignored. A valid ID with no stored reward returns `404 reward_not_found`. Client-supplied identity, balance, cost, and snapshot fields are never used.

```http
POST /api/redemptions
x-user: 1
Idempotency-Key: 8b9f20f4-7b42-4c90-a02c-733f6a8d1e55
Content-Type: application/json
Accept: application/json

{"reward_id": 1}
```

Success: `201 Created` for both the first success and a replay. A replay returns the original response body, including the same redemption ID, timestamp, snapshots, and transaction balance.

```json
{
  "redemption": {
    "id": 42,
    "reward_id": 1,
    "reward_name": "Free coffee",
    "points_spent": 250,
    "created_at": "2026-10-04T20:00:00.000Z"
  },
  "points_balance": 1000
}
```

The response balance is the result of this transaction; a later concurrent transaction can change it again. The redemption object has the same fields as a history entry.

Required write behavior:

1. Use Rails request parsing, resolve the demo user from `x-user`, require the JSON media type, validate the JSON body’s positive integer `reward_id`, and validate the required UUID v4 header. Uppercase hexadecimal is accepted and normalized to lowercase. Whitespace, multiple values, and other UUID versions are rejected.
2. Begin a SQLite `BEGIN IMMEDIATE` transaction and read fresh database state with the Rails query cache disabled. Look up a committed redemption by `(user_id, idempotency_key)` before checking current reward availability or balance.
3. If the key exists for the same `reward_id`, return its saved success without another debit. If it belongs to a different reward, return `409 idempotency_conflict` without mutation.
4. For an unused key, verify that the reward exists and is active, then compare the stored balance with the stored reward cost. Never use client-supplied balance or cost.
5. Atomically deduct points and insert history with the key, `reward_name`, `points_spent`, and the resulting `points_balance_after` snapshot. Commit before returning success. Rollback removes both the debit and the key/result.

SQLite's database write lock serializes this lookup and write across connections and processes, including reward edits. A database unique index on `(user_id, idempotency_key)` additionally prevents duplicate committed keys. Concurrent requests with the same user/key/reward all receive the same success when the lock can be acquired; they produce one debit and one history entry. Different keys represent different purchases and may legitimately charge more than once. The SQLite adapter waits for a write lock using the configured 5-second timeout. The application makes one transaction attempt; busy/locked failures roll back and return `503 service_unavailable`. Retry the request with the same key.

Errors: identity errors above; `415 unsupported_media_type`; `400 invalid_json`; `400 missing_idempotency_key`; `400 invalid_idempotency_key`; `409 idempotency_conflict`; `422 invalid_request`; `404 reward_not_found`; `422 reward_inactive`; `422 insufficient_points`; and `503 service_unavailable` for database contention.

#### Idempotency key lifecycle

- **Generate and persist before POST:** use `crypto.randomUUID()` when the user confirms a new redemption. Save `{ userId, rewardId, key }` in `sessionStorage` before sending the request. If storage cannot be read or written, block new submissions. The key is an HTTP header, not an extra JSON body field.
- **One unresolved attempt per tab:** keep its original user, reward, and UUID across navigation and page refreshes. A retry must send the same identity, header, and body. Disable new purchases and identity changes while this attempt is unresolved. Tabs have separate storage; independent actions in separate tabs are separate redemption intents.
- **Uncertain outcomes:** retain the saved attempt after timeouts, connection loss, unreadable/malformed success responses, unexpected errors, or `5xx` responses (including `503`). The UI offers an explicit “Retry saved redemption” action. Recovery does not depend on reward affordability or the reward still appearing in the active catalog. No automatic POST retry is performed by the frontend.
- **Resolve by replay:** balance/history reads alone cannot identify this request's outcome and never clear the key. Retry the saved POST. A valid success clears the saved attempt; a documented validation/domain rejection clears it because no redemption was committed. `409 idempotency_conflict` keeps it blocked for investigation; never silently replace a conflicting key. An explicit “Discard saved request (I’ve checked my history)” action clears a saved request after the user checks history for its original identity. It also recovers corrupt storage. Discard does not undo a committed charge or prove an ambiguous request failed; the next purchase uses a new key and may charge again. If storage cannot be cleared and read, the UI stays blocked and directs the user to allow site storage in browser settings.
- **Start a new intent:** after success or a definitive validation/domain rejection, the next user-confirmed purchase receives a new UUID, even for the same reward. Canceling or navigating away from an unresolved purchase does not discard its key.
- **Retention and scope:** successful keys remain stored with their redemption indefinitely, scoped to the selected user and this POST operation. There is no expiry or key cleanup. Validation/domain failures are not cached and do not consume a key; a later retry may succeed if database state changes. History created before this migration has no key or original balance snapshot and cannot be replayed. Newly seeded redemptions use the same service with their own UUIDs.
- **Replay balance:** `points_balance` is the original transaction's saved balance, which may differ from today's balance after subsequent purchases. Fetch `GET /api/balance` for the current balance; refresh rewards and history after success as well.

Example: two simultaneous requests for user `1`, reward `1`, and key `8b9f20f4-7b42-4c90-a02c-733f6a8d1e55` create redemption `42` once and both return the illustrated `201` body. Retrying that key after a lost response returns redemption `42` again. Buying another coffee requires a new key. Sending reward `2` with the committed key returns `409`.

#### Idempotency key flow

```mermaid
sequenceDiagram
    actor User
    participant FE as React frontend
    participant Storage as sessionStorage (tab)
    participant API as Rails API
    participant DB as SQLite

    User->>FE: Confirm a new redemption
    FE->>FE: Generate UUID v4 K
    FE->>Storage: Save user, reward, K before POST
    FE->>API: POST reward_id + x-user + Idempotency-Key K
    API->>DB: BEGIN IMMEDIATE; find user + K
    alt Key already committed for the same reward
        DB-->>API: Saved redemption and original balance
        API->>DB: COMMIT read transaction
        API-->>FE: Replay original 201 body; no debit
    else Key committed for a different reward
        API->>DB: ROLLBACK
        API-->>FE: 409 idempotency_conflict; no debit
        FE->>Storage: Keep saved attempt; block new purchases
    else Key unused
        API->>DB: Validate reward and balance
        alt Valid redemption
            API->>DB: Debit + history + K + balance snapshot; COMMIT
            API-->>FE: 201 with committed result
        else Validation or domain rejection
            API->>DB: ROLLBACK; no debit or saved key
            API-->>FE: 4xx validation/domain error
        end
    end
    alt Conflict received
        FE->>FE: Keep key; resolve conflict before a new purchase
    else Valid success or definitive rejection received
        FE->>Storage: Clear saved attempt
        FE->>FE: Next confirmed purchase generates a new UUID
    else Lost response, timeout, 5xx, or unreadable result
        Note over FE,Storage: Keep the original user, reward, and K
        User->>FE: Reload page or navigate
        FE->>Storage: Restore unresolved attempt and identity
        Note over FE: Balance/history reads do not clear K
        User->>FE: Retry saved redemption
        FE->>API: Same POST body, x-user, and K
        Note over API,DB: Repeat locked lookup; replay if already committed
    end
```

### GET /api/redemptions

No request body or query parameters. Returns all redemptions belonging to the user selected by `x-user`, ordered by `created_at` descending, then `id` descending.

```http
GET /api/redemptions
x-user: 1
Accept: application/json
```

```json
[
  {
    "id": 42,
    "reward_id": 1,
    "reward_name": "Free coffee",
    "points_spent": 250,
    "created_at": "2026-10-04T20:00:00.000Z"
  }
]
```

`reward_name` and `points_spent` are historical snapshots. Later changes to a reward's name, cost, or active status do not alter or remove prior history entries. The response includes only the five fields shown above.

Errors: `400 missing_user_header`, `400 invalid_user_header`, `404 user_not_found`.

## Error contract

All API errors use the same JSON envelope. Clients should branch on the HTTP status and stable `error.code`; `message` is human-readable and may change. `details` is always an object, empty when there is no additional context. Never expose stack traces, SQL, or internal exception text.

```json
{
  "error": {
    "code": "insufficient_points",
    "message": "You do not have enough points to redeem this reward.",
    "details": {
      "points_balance": 100,
      "points_required": 250
    }
  }
}
```

| HTTP status | `error.code` | Condition | `details` |
| --- | --- | --- | --- |
| 400 | `missing_user_header` | `x-user` is absent or blank. | `{}` |
| 400 | `invalid_user_header` | `x-user` is not one positive decimal integer in the accepted format. | `{}` |
| 400 | `missing_idempotency_key` | POST `Idempotency-Key` is absent or blank. | `{}` |
| 400 | `invalid_idempotency_key` | POST key is not a single UUID v4 in canonical hyphenated form. | `{}` |
| 400 | `invalid_json` | Request body cannot be parsed as JSON. Rails treats an empty body as empty parameters. | `{}` |
| 404 | `user_not_found` | A valid `x-user` value does not identify an existing user. | `{}` |
| 422 | `invalid_request` | JSON body lacks a positive integer reward ID in the accepted format. | `{}` |
| 404 | `reward_not_found` | A valid `reward_id` does not identify an existing reward. | `{}` |
| 404 | `endpoint_not_found` | No API route exists for the requested path. | `{}` |
| 405 | `method_not_allowed` | Path exists but does not support this HTTP method. Include an `Allow` header with the supported methods. | `{}` |
| 409 | `idempotency_conflict` | This user already committed this key for a different `reward_id`. | `{}` |
| 415 | `unsupported_media_type` | POST content type is missing or is not JSON. | `{}` |
| 422 | `reward_inactive` | The reward exists but is inactive when redemption is attempted. | `{"reward_id": 1}` |
| 422 | `insufficient_points` | Stored balance is lower than the stored reward cost. | `{"points_balance": 100, "points_required": 250}` |
| 503 | `service_unavailable` | Database contention prevents completion of the single transaction attempt (write-lock waiting is bounded by the configured 5-second timeout); this request has committed no changes. | `{}` |
| 500 | `internal_error` | An unexpected server failure occurs. | `{}` |

The controller resolves the demo identity first, then checks the POST media type, parses and validates the JSON body reward ID, and validates the idempotency key. For example, missing identity wins over malformed JSON; malformed JSON with valid identity and media type returns `400 invalid_json`. Reward existence is checked in the transaction. Inside the transaction, check the committed key first: replay or conflict takes precedence over reward existence, active status, and sufficient points. Unknown routes and unsupported methods return their documented errors when request parsing succeeds. No `401` or `403` responses are specified because authentication and authorization are out of scope.

Domain and validation errors do not change points or create history. A `500` or network failure can leave the client uncertain whether a transaction committed; retain the original idempotency key and retry the same POST to resolve the outcome. A balance/history refresh alone does not resolve it.

## Health check

`GET /up` is an existing operational Rails health check, outside the four challenge API endpoints. It does not require `x-user`, returns Rails' health response (HTML), and does not use the API error envelope.
